# ADR-002 - Stable node ID strategy

Status: Accepted  
Date: 2026-08-07

## Context

Node identity must be unique, persistent, serializable, stable through save/load, and
usable as a map/set key. Indices, traversal positions, and memory addresses do not meet
those requirements.

## Decision

Use a `NodeId` newtype around UUID v4 values generated by the `uuid` crate. `NodeId`
implements equality, ordering, hashing, display, and Serde string serialization. The
document registry is a `BTreeMap<NodeId, Node>` for deterministic traversal, while sibling
z-order remains an explicit `Vec<NodeId>`.

Duplicate IDs are rejected both at registration and at the validated load boundary.

## Alternatives considered

- Vector indices: compact but unstable under insertion/deletion and explicitly prohibited.
- Monotonic process-local integers: deterministic but unsafe for merging/importing
  independently created documents.
- ULID/UUID v7: time-sortable, but sort order is not a semantic requirement for nodes.

## Why this decision

UUID v4 provides decentralized creation with negligible collision risk and no coupling to
storage order. A domain newtype prevents accidental mixing with renderer or resource IDs.

## Tradeoffs

UUIDs use more storage than integers and are not human-friendly. JSON stores canonical
strings for inspectability and interop.

## Boundary impact

`uuid` is used only by the document identity type. UUID strings cross the serialization
boundary; the UUID crate does not own hierarchy or document semantics. The dependency is
MIT/Apache-2.0 and can be replaced behind `NodeId` with a schema migration.

## Migration / reversibility

The newtype contains the dependency. A future ID format would require explicit file-schema
migration but would not affect hierarchy APIs.

## Future impact

Stable IDs can address typed commands, animation properties, semantic AI targets, imports,
and interop mappings without referring to runtime object locations.
